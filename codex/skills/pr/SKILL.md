# pr: PR 本文のフォーマット

PR 本文の **形** を定めるスキル。ワークフローではない。ブランチの push、PR の作成、何を PR に含めるかの判断はしない。PR 本文を書くときに、本文がどうあるべきかだけを定める。

レビュアーは diff を開いている。本文の役割は、diff を読む前に **変更の形** と **どこを慎重に読むべきか** を渡すこと。散文で diff をなぞらない。

## テンプレート

3 セクションをこの順で書く。前置き（「この PR では〜」「概要:」など）は置かず、本文は `## Summary` から始める。

````markdown
## Summary

<1〜2 文: 何がどう変わったか>

<最小のビュー（下記から 1 つ、多くても 2〜3 個）>

## Evidence

**Before:** <失敗していたテスト / 旧出力 / スクリーンショット>
**After:** <通るようになったテスト / 新出力 / スクリーンショット>

## Merge Danger

- **Door:** 双方向（two-way） / 一方通行（one-way） — <理由を 1 文>
- **Blast radius:** <間違っていたら何が壊れるか>
````

本文は日本語で書く（コード識別子・コマンドは原文のまま）。見出しは上記の英語のままでよい。

## Summary: 最小のビューを選ぶ

要点が伝わる **最小** のビューを 1 つ選び、その横に短い説明を添える。複数使うのは、1 つでは要点が伝わらないときだけ。全部使うことはほぼない。

| 変更の性質 | ビュー |
|---|---|
| ロジック・アルゴリズムの変更 | 擬似コード |
| 呼び出し関係の変更（新しい経路、処理の差し込み） | コールツリー |
| UI コンポーネントの構成変更 | コンポーネントツリー |
| ファイルの追加・移動・削除が主 | ファイルツリー |
| 状態遷移・シーケンス・システム間の境界 | Mermaid 図 |
| 数行の変更が核心 | 要点だけに絞った diff（shaped diff） |

共通ルール:

- レビュアーに必要な呼び出し・ファイル・props・境界だけを残す。無関係なノードは削る
- ツリーでは変更箇所に印を付ける（例: `+` 追加、`~` 変更、`-` 削除、`← NEW`）
- 散文は短く。ビューを読めば分かることを文章で繰り返さない

例（コールツリー）:

```
handleCheckout()
├─ validateCart()
├─ applyCoupon()        ← NEW: 期限切れクーポンを弾く
└─ chargePayment()
```

例（ファイルツリー）:

```
claude/skills/
├─ pr/SKILL.md          + 追加
└─ pr-review-guide/     ~ description のみ変更
```

Mermaid は GitHub / GitLab の PR 本文ではレンダリングされるが、ターミナルでは生テキストに見える。ユーザーにローカルで見せる段階で読みにくければ、ツリーや擬似コードを優先する。

## Evidence: before と after を示す

「テストが通った」は主張であって証拠ではない。必ず **before / after** の対で示す。

優先順位:

1. **スクリーンショット**: 見た目の変更で、環境的に撮れる場合に最強
2. **失敗→成功したテスト**: 該当テストを擬似コードで書き、before で落ち after で通ることを示す
3. **変わったコンソール出力**: コマンドと、前後の出力の差分

```
test "期限切れクーポンは適用されない":
  cart に期限切れクーポンを適用
  expect 合計金額 == 元の金額
# before: FAIL（割引が適用されていた）  after: PASS
```

UI のない変更（マイグレーション、バックグラウンドジョブ、リファクタ）でもスクリーンショット以外は使える。リファクタなら「振る舞いが変わらないこと」を示すテストや出力を before / after で示す。

実際に実行していない結果を書かない。実行できなかったなら「未検証」とそのまま書く。

## Merge Danger: ドアと影響範囲を宣言する

このセクションが本スキルの中心。「マージして安全か」を勘ではなく、レビュアーが反論できる **明示的な主張** にする。

- **双方向のドア（two-way door）**: 安く元に戻せる。revert で完全に戻る
- **一方通行のドア（one-way door）**: 戻せない、または戻すのが高くつく

一方通行として扱うもの（迷ったら一方通行側に倒す）:

- 破壊的なデータベースマイグレーション、データの削除・形式変換
- public API・CLI・設定キーの削除や非互換変更
- 外部に出ていく副作用（メール・通知・Webhook の送信、外部サービスへの書き込み、公開・デプロイ）
- フラグ付きロールアウトでも、新形式での書き込みが一度でも起きるもの（最初の書き込み以降は戻せない）
- 秘密情報・権限・認証まわりの変更

「commit を revert してもメールの送信は取り消せない」。diff の見た目ではなく、**本番で起きた結果を戻せるか** で判定する。

**Blast radius** には、変更が間違っていた場合に壊れるものを具体的に書く（例: レイアウトずれ、API の利用側、モバイル表示、特定ジョブの全件処理）。「影響は限定的」のような曖昧な表現は使わない。

自分で書いた変更を自分で採点している点を自覚する。「双方向・影響小」と判定するときほど根拠を具体的に書く。チケットや仕様が手元にあれば、diff だけでなくそれも踏まえて判定する。

## リポジトリ固有の規約との関係

- リポジトリに `.github/pull_request_template.md` などの PR テンプレートがある場合は、**リポジトリのテンプレートを優先** して埋め、その中（概要・説明欄など）に Summary / Evidence / Merge Danger を収める。テンプレートの項目を削除しない
- リポジトリの CLAUDE.md / AGENTS.md に「常に一方通行として扱う変更」や本文末尾の定型文（LLM 生成の明記など）の指定があれば従う
- PR タイトルはプロジェクト規約に従う（規約がなければ Conventional Commits 形式・日本語）

## やらないこと

- PR の作成・push（作成を頼まれた場合は、本文をこの形で書いたうえで `gh pr create` 等を別途使う）
- 巨大な PR の分割。本文が巨大になるのは PR が大きすぎるためであり、その場合はユーザーに分割を提案する
- レビューコメントのトリアージ
- 本文の自動更新。PR が大きく変わったら、依頼に応じてこの形で書き直す

## チェックリスト（書き終えたら確認）

- [ ] 本文が `## Summary` から始まっている（前置きがない）
- [ ] Summary のビューだけで、diff を開く前に何が変わったか分かる
- [ ] Evidence が before / after の対になっている（「テスト green」だけで終わっていない）
- [ ] Merge Danger にドアの判定と理由、具体的な blast radius がある
