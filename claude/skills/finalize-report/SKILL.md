# レポート完成版化（finalize-report）

増築された文書を「完成品」に書き直すスキル。核となる考え方は1つ:

> 増築文書は **書かれた順** に並んでいる。完成版は **読まれる順** に並べ直す。

追記を重ねた文書には、書き手と依頼者の対話の歴史（「〜を追加」「検討中(8/25時点)」「前章で述べた通り修正」）が堆積する。初見の読者にとってこれはノイズであり、本質の理解を妨げる。一方で、堆積の中には失ってはいけない実質（事実・決定・トレードオフ）が混ざっている。このスキルの仕事は **経緯を落とし、実質を残し、読まれる順に組み直す** こと。

## 手順

### 1. 現物の全体を取得する

- 対象文書の全文を読む（媒体は問わない。書き戻しに使う形式で取得しておく）
- 部分だけ見て書き直さない。重複や相互参照は全体を見ないと検出できない

### 2. 除去対象を特定する（経緯の痕跡）

以下は完成版に存在してはならない。見つけたら削除するか、状態情報だけに変換する。

| 種別 | 例 | 処理 |
| --- | --- | --- |
| 文書自身の変遷への言及 | 「〜を追加」「進化版」「前回の指摘を受けて」「v2」「改訂版として」 | 削除。内容は本文に溶かす |
| 時点・予定の記述 | 「8/25時点で検討中」「来週打ち合わせ予定」「現在調査中」 | ステータスラベル（済/検討中/未対応）だけ残し、日付・予定は削除 |
| 会話の痕跡 | 「ご指摘の通り」「上記の質問に対して」「補足すると」の連鎖 | 削除し、地の文として書き直す |
| 調査プロセスの語り | 「調査した結果判明した」「〜を確認したところ」 | 結論を直接述べ、根拠は出典リンクで示す |
| 後付け注記の連鎖 | 本文と矛盾を「※ただし〜」で継ぎ足した箇所 | 本文自体を修正して注記を消す |
| 章番号のドリフト | 追記による欠番・枝番（5-2 だけ肥大など） | 振り直し、相互参照も更新 |

### 3. 保全対象を確認する（実質）

削除・圧縮の前に、以下が1つも落ちないことを保証する。**判定基準は「読者の行動が変わる情報か」**。変わるなら実質、変わらないなら経緯。

- 事実・数値・観測データ・ログの引用
- 決定事項と **その根拠**、検討して不採用にした選択肢と **不採用の理由**
- トレードオフ・リスク・前提条件（受容したリスクは受容の前提ごと）
- ステータス（実装済み/検討中/未対応）— 状態は実質、日付と経緯はノイズ
- 出典 URL・チケット番号・関連文書へのリンク

### 4. 読まれる順に再構成する

- **冒頭に要点サマリー**（3行程度・結論先出し）。読者がここだけ読んでも文書の結論がわかること
- 章立ては読者の問いの順: 何が起きたか → なぜか → どうしたか → 何が残っているか → 参考
- **同じ内容を伝える図と表が両方あるなら、情報量の多い方を1つ残す**（増築文書の典型的な重複）
- 詳細派生物（コード差分・長大な対比表）は、要点が別の形で伝わるなら削除する
- 章間の相互参照（「第N章参照」）を振り直し後の番号に合わせる

### 5. 表現を最小化する

- 表のセルは1〜2文。修飾語・重複強調を削る
- 削るのは **文字数** であって **情報** ではない。圧縮の結果、専門でない関係者が読めなくなったら圧縮しすぎ
- 略語・コードネームは初出で一言補足する（読者は経緯を知らない前提）
- 強調（太字・ステータスラベル・パネル）は「読者が見落とすと判断を誤る箇所」だけに絞る

### 6. 検証して書き戻す

1. **差分セルフチェック**: 旧版と新版を突き合わせ、保全対象（手順3）が欠落していないか確認する。特に「不採用の理由」「受容の前提条件」は落としやすい
2. 相互参照・リンク・章番号の整合を確認
3. **同じ文書を上書き更新する**（新しい文書・別ファイルを作らない。URL やパスは維持する）。更新コメントを付けられる媒体なら「完成版として再構成」程度に簡潔に
4. ユーザーへの報告は「何を削り、何を残し、構成をどう変えたか」を短く

## 判定例

**削除する（経緯）:**
- 「6-4. 対応案の比較（調査に基づく進化版）」→ 見出しは「対応案」だけにする
- 「検討中（8/25時点。チーム内打ち合わせで相談予定 — 管理簿の補足参照）」→ ステータス「検討中」のみ
- 「本章の対応案は、AWS 公式・業界標準を調査した結果に基づく」→ 削除し、各案に出典リンクを付ける

**残す（実質）:**
- 「可逆匿名化は、ベクトル検索が元の固有名詞に依存するため検索劣化が解消せず不適」→ 不採用案と理由は完成版の中核
- 「前提条件: RAG データ源に個人の電話番号を含めないこと」→ 受容の前提。落とすと将来の変更者が事故る
- 「実装済み」「検討中」のステータスラベル → 状態は読者の行動を変える

## 注意

- 内容の正誤判定や新情報の追加はこのスキルの仕事ではない。書き直し中に事実の矛盾を見つけたら、勝手に直さずユーザーに報告する
- 元の文書が失われる操作なので、バージョン履歴のない媒体（生ファイル等）では上書き前に旧版のバックアップを取る。履歴管理された媒体ではそのまま上書きしてよい
