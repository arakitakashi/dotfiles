# 図（シーン）の設計

図はこのサイトの主役で、画面の最大面積を占める。文章は図の変化を説明するためにある。

## 1. 宣言的なシーン

各ステップは、図の**完全な状態**（何がどこにあり、何とつながり、何が流れているか）をデータで宣言する。
アニメーションは書かない。エンジンが前のステップとの差分を取り、「退場 → 移動 → 登場 → 線を引く → 粒子が流れる」の順で補間する。

このため、次の 2 点が品質を左右する。

- **同じ物には、ステップをまたいで同じ `id` を付ける。** id が変わると「消えて、別の物が現れた」と解釈される
- **同じ物は、同じ位置に置き続ける。** 理由なく動かすと、読者は動いたこと自体に意味を探す

レッスンごとに図を組み立てるヘルパー関数を書き、各ステップは「何が違うか」だけを引数で渡す。
`src/content/lessons/event-loop.ts` の `scene()` が手本になる。

## 2. 題材の記号体系を先に決める

レッスンを書く前に、コース全体で使う記号を `src/content/course.ts` で固定する。

| 定義 | 決めること | 目安 |
|---|---|---|
| `roles` | 登場する物の役割 → 色（Hue）とアイコン | 6〜10 個。同じ役割は必ず同じ色 |
| `flowKinds` | 図を流れる粒子の種類 → 色と形 | 4〜8 個。正常・異常・重い・戻りなど、意味の違いで分ける |
| `metrics` | 指標 → 名前・単位・閾値 | コース全体で 8〜20 個。レッスンは 3〜5 個を選ぶ |
| `projection` | `iso`（等角のジオラマ）か `flat`（平面の構成図） | 下の表を参照 |

色は 9 種（sand / green / blue / violet / amber / red / teal / rose / slate）から選ぶ。
`red` は「悪い状態・攻撃・失敗」のために空けておくと、図の中で異常が一目でわかる。

色が足りなくなったら、色を増やさずに次の順で解く。

1. **粒子は、行き先や出どころの役割と同じ色にする。** 「借方への記入」は資産と同じ色、のように意味がつながるなら、同じ色のほうがむしろ読みやすい。粒子同士は形（dot / square / diamond / ring）で区別する
2. **脇役をまとめる。** 外部の相手、補助的な部品は `sand` か `slate` に寄せ、主役に色を割り当てる
3. **同時に画面に出ない役割は、同じ色を共有する**

| 投影 | 向いている題材 |
|---|---|
| `iso` | 物理的な配置や規模感があるもの。サーバー構成、ネットワーク、工場、都市、細胞、倉庫 |
| `flat` | 論理的な関係が主のもの。データ構造、状態遷移、コンパイラの工程、数式の変形、組織 |

迷ったら `iso`。立体のブロックは「物」として認識されやすく、粒子の流れが映える。
文字の多いカード（`queue`・`panel`）が主役になる題材は `flat` のほうが読みやすい。

## 3. エンティティの種類と選び方

| kind | 見た目 | 使いどころ |
|---|---|---|
| `block` | 立体のブロック（flat では角丸の箱） | 処理する主体。サーバー、関数、工程、器官 |
| `store` | 円柱（flat では上に線のある箱） | 溜める場所。データベース、ファイル、在庫、記憶 |
| `actor` | 台座の上の人物アイコン | 外から働きかける主体。利用者、攻撃者、クライアント。`count` で群衆にできる |
| `zone` | 床の領域（破線の枠） | 境界。リージョン、プロセス、信頼境界、部署 |
| `queue` | 枠が並んだカード | 順番待ち、スタック、バッファ、配列。`layout: 'stack'` で縦積み |
| `panel` | 情報カード | 内訳の表（`rows`。`head` で列見出し、行ごとに状態色）、コードや式（`lines`）、割合の棒（`bars`）。`role` を付けると見出しの帯がその色になる。帳簿・表・一覧のように「中身を読むカード」はこれを使い、`queue`（順番待ちの意味を持つ）を流用しない |
| `note` | ピル型のラベル | 図の中の短い注記 |
| `custom` | 自分で描く SVG | 上のどれにも当てはまらない、題材固有の形（10 節） |

状態（`state`）で、同じ物の様子を変えられる。

| state | 見た目 | 意味 |
|---|---|---|
| `ok` | 通常 | — |
| `hot` | 赤い輪郭が明滅 | 過負荷、異常、攻撃を受けている |
| `down` | 灰色で薄い | 停止、故障 |
| `dim` | 薄い | いまは関係しない、使われていない |
| `ghost` | 破線の輪郭 | これから置かれる予定、仮想的なもの |
| `focus` | 太い輪郭と光 | このステップの主役 |

`block` には `gauge`（0〜1 のメーター）、`tag`（「DOWN」などの小さな札）、`pill`（下に出す短い注記）を付けられる。
負荷・充填率・進み具合のように 1 つの量で状態を表せるものは、`gauge` にすると変化が動いて見える。

名前（`label`）は短くする。iso のブロックは上の面に全角 4 字（半角なら 8 字）まで載り、それを超えると自動で下のピルに出る。
補足は `sub` に分ける。

## 4. 配置

座標は `[列, 行]`。右が列の正、下が行の正で、0.5 刻みで置ける。iso では 1 列 = 104 px、1 行 = 52 px。

- **流れは左から右、上から下。** 原因を左上、結果を右下に置く
- **段で意味を分ける。** たとえば上段は「処理する物」、下段は「待っている物・溜まっている物」
- **題材が軸を持つなら、位置にその意味を持たせる。** 借方は左・貸方は右、送信側は左・受信側は右、過去は左・未来は右、低い層は下・高い層は上。位置が意味を運ぶと、読者は場所を見るだけで分類できる。決めた軸は全レッスンで守る
- **iso では斜めに置くと美しい。** 列と行を同じだけ動かした位置（`[0,0]` → `[2,2]` → `[4,0]`）は、線が床の目にぴったり沿う。縦に場所を取りすぎるときは行の差を半分にしてもよい（`[0,0]` → `[2,1]` → `[4,0]`。サンプルはこちら）
- **ブロック同士は 2 列以上離す。** 間にリンクのラベルが入る余地が要る
- **図全体を 1080×740 px 以内、縦横比 3:2 前後に収める。** デスクトップの図の枠は約 670×460 px で、文字が読める最小の倍率（0.62）を下回るとカメラが一部に寄り、全体が映らなくなる。目安は iso で横 10 列 × 縦 14 行、flat で横 6 列 × 縦 6 行まで。これを超えると検証スクリプトが `scene-size` の警告を出す。「後で増える物の場所を空けておく」のは、この大きさの内側で行う。収まらないなら、最後のステップまでに出てくる物を数え直し、カードの `capacity` を減らすか、レッスンを分ける
- **後のステップで増える物の場所を、最初から空けておく。** 途中で全体を詰め直すと、読者は何が変わったのかわからなくなる。空けた場所に仮の印を置きたいときは、別の物を置かず、後で来る物と**同じ id** を `state: 'ghost'`（破線の輪郭）で先に置く。本物になるステップでは `state` を外すだけで済み、重なりも起きない
- カード（`queue`・`panel`）は場所を取る。`capacity` は見せたい最大数に絞る（3〜4）

物が重なっていると `npm run validate` が `overlap` の警告を出す。ただし線の交差やラベルの重なりは機械で拾えないので、撮影して目で確かめる（11 節）。

## 5. リンクと粒子

### リンク

| style | 見た目 | 意味 |
|---|---|---|
| `solid` | 実線の矢印 | 通常の依存・呼び出し |
| `dashed` | 破線 | 非同期、任意、ゆるい関係 |
| `off` | 薄い破線 | いまは使われていない経路 |
| `beat` | 緑の点線が流れる | 定期的な確認（死活監視など） |
| `cut` | 赤い破線 | 切断、遮断 |

- ラベルは全角 6 字程度まで。動詞で書く（「預ける」「描き直す」）
- 他の物を横切るときは `via` で折れ線にする
- 経路の意味が変わったら、物を動かさずに `style` を変える（`solid` → `off` → `cut`）。同じ場所で線だけが変わるので、変化が際立つ

### 粒子（flows）

粒子は、静止画では伝わらない**振る舞い**を見せるためにある。偏り、渋滞、迂回、往復、扇状の広がり。

| 指定 | 効果 | 使いどころ |
|---|---|---|
| `rate` | 1 秒あたりの数 | 負荷の大小。増やすと混雑が見える |
| `route` に配列 | そこで分岐 | 振り分け、複製。`pick: 'rr'` で順番、数値配列で重み付き |
| `pattern` | 種類を順に切り替える | 軽い・軽い・重い、のような混在 |
| `bounce` | 終点で折り返す | 要求と応答 |
| `end: 'burst'` | 終点で赤く弾ける | 失敗、拒否、タイムアウト |
| `end: 'pop'` | 終点で緑の輪が広がる | 成功、完了 |
| `speed` | 速さ | 遅い経路と速い経路の対比 |

- 1 つの図に流す粒子は 2〜4 系統まで。多すぎると何も読めない
- 粒子が表すのは「流れ続けるもの」。1 回きりの出来事や、2 か所が同時に変わること（1 つの取引が左右に同額を記入する）は粒子では表しにくい。その場合は、物の中身の変化（`panel` の行が増える、`gauge` が動く）で見せ、粒子は「どこからどこへ」の向きを示す補助にとどめる。同時に流したい 2 本は `rate` と `speed` をそろえる
- `problem` のステップでは、粒子で壊れ方を見せる（弾ける、詰まる、1 か所に偏る）
- 凡例には、その図に流れている種類だけが自動で出る

## 6. 1 ステップ 1 差分

読者が 1 ステップで追える変化は、主なもの 1 つと、それに伴うもの 2〜3 個まで。

- 物を足すステップ: 物 1 つ + それにつながる線 1〜2 本
- 壊すステップ: 物は増やさず、`state`・`gauge`・線の `style`・粒子の種類を変える
- 数値を上げるステップ: 図は同じで、`rate`・`gauge`・指標だけ変える

検証スクリプトは、差分が 0（図が変わらない）と 10 以上（多すぎる）のステップに警告を出す。
変化が多くなるのは、たいてい 2 つのステップを 1 つにまとめているとき。

差分の数え方:

| 変化 | 数 |
|---|---|
| 同じ id の物の中身・状態・位置が変わる | 1 |
| 物が現れる / 消える | 各 1 |
| 線が現れる / 消える / `style`・`label` が変わる | 各 1 |
| 粒子（`flows`）だけが変わる | 0（ただし「図が変わらない」の警告は出ない） |

id を付け替えると「消える + 現れる + つながる線の数だけ消えて現れる」になり、一気に増える。
役割が変わるだけの物（ノートが仕訳帳になる、候補がリーダーになる）は、**同じ id のまま中身を変える**。

変化した物には、エンジンが一瞬だけ光を当てる。小さな画面では、カメラが変化した部分に自動で寄る。

## 7. 指標

指標は「その変化は良かったのか、悪かったのか」を数値で示す計器で、図の左上に常に出る。

- **読者にとっての結果を測る。** 内部の量（スレッド数）より、体感に近い量（応答までの時間、失敗した要求の割合）
- **名前は具体的に。** 「レイテンシ」より「操作への応答」
- **閾値を必ず決める。** 良・注意・悪の境目が、数値に手触りを与える。根拠のある数字（1 フレーム 16.7 ms、ロングタスク 50 ms）を使う。「良い」の形は題材で違うので、`src/tones.ts` から合うものを選ぶ: 小さいほど良い `below`、大きいほど良い `above`、ぴったりであるべき `exactly`（貸借の差、取りこぼし、不整合の件数）、範囲に収まるべき `within`
- **良し悪しのない量は、無理に色を付けない。** 単に見せたい数（残高、件数）は `plain` にする。指標のうち 1 つか 2 つが悪化すれば十分で、全部を悪化させる必要はない
- **図の中の数値と一致させる。** カードやラベルに出した数と、指標・本文・差分リストの数が食い違うと、読者はどれを信じてよいかわからなくなる。数は 1 か所で計算し、図と指標の両方に同じ値を渡す
- **レッスンの中で悪化させる。** ずっと緑の指標は情報を持たない。`problem` のステップで赤くなり、`solution` で戻る
- まだ測れない値、まだ意味を持たない値は `null`（「—」と表示）。後のステップで埋まっていく演出になる。レッスンの途中で初めて登場する指標（書き込みの費用など）は、それまで `null` にしておけばよい
- 数値は本文と差分リストにも書く（「4 ms → 3,000 ms」）

## 8. 予測問題とつまみの図

**予測問題**は、結果を見せるステップそのものに置く。読者が答えるまで図は 1 つ前の状態で止まり、本文も隠れる。
答えた瞬間に図が動いて答えを見せるので、そのステップの図は「答えが目で見てわかる」ものにする。
止まるのは「次へ」と → キーによる前進だけで、タイムラインや URL から先のステップへ飛ぶことはできる（共有された URL を開けなくしないため）。

**つまみ**のあるステップは、`sceneFor(values)` と `metricsFor(values)` で、値に応じた図と指標を返す。

- 図の構造（物と線）は変えず、`gauge`・`state`・粒子の `rate`・カードの中身を変える
- つまみの使い方は 2 つある
  - **トレードオフを探る**: 良くなる方向と悪くなる方向の両方を用意し、閾値をまたぐ値を範囲に含める（指標の色が変わる瞬間が、いちばんの学び）
  - **不変条件を体感する**: どう動かしても変わらない量があることを見せる（売上をいくらにしても貸借の差は 0、どの順で足しても合計は同じ）。動く指標と動かない指標を並べる
- 最小値と最大値の両方で図が壊れないこと（検証スクリプトが両端で検査する）
- 値の見せ方は `format` で変えられる。段階の名前を出す（`(v) => ['弱', '中', '強'][v]`）、桁をまたぐ量を対数で動かす（つまみを指数にして `format: (v) => \`${10 ** v} 行\``、`sceneFor` でも `10 ** v` を使う）

## 9. 題材別の組み立て例

| 題材 | 主役の物 | 流れる粒子 | 指標 |
|---|---|---|---|
| Web の実行モデル | メインスレッド、スタック（`queue`）、キュー、Web API | 操作、タスク、描画 | フレーム時間、応答の遅れ、待ちの数 |
| データベースの索引 | テーブル（`store`）、索引の木（`custom`）、問い合わせ | 読んだ行、索引の探索 | 読んだ行数、応答時間、書き込みの費用 |
| Git の内部 | 作業ツリー、索引、オブジェクト（`queue`）、参照 | blob・tree・commit | オブジェクト数、到達できないコミット |
| 機械学習の訓練 | データ、モデル、損失（`panel` の棒）、最適化 | バッチ、勾配 | 訓練損失、検証損失、その差 |
| 会計の仕訳 | 取引、仕訳帳、元帳（`panel`）、試算表 | 借方、貸方 | 貸借の差、利益、現金 |
| 免疫のしくみ | 病原体（`actor`）、各種の細胞、リンパ節（`zone`） | 抗原、抗体、信号 | 病原体の数、応答までの日数 |

どの題材でも、問うことは同じ。「何が**物**で、何が**流れ**で、何を**測る**か」。

## 10. 題材固有の図形（custom）

木、リング、グラフ、波形のように、用意された種類で表せない形は `Course.renderers` に描画関数を登録する。

```ts
renderers: {
  ring: {
    // 原点 (0,0) を中心にした SVG 文字列を返す
    draw: (e, ctx) => {
      const nodes = (e.props?.nodes as string[]) ?? [];
      const r = 90;
      const dots = nodes.map((n, i) => {
        const a = (i / nodes.length) * Math.PI * 2 - Math.PI / 2;
        return ctx.pill(n, Math.cos(a) * r, Math.sin(a) * r * 0.5, { tone: 'neutral' });
      }).join('');
      return `<ellipse class="outline" cx="0" cy="0" rx="${r}" ry="${r * 0.5}"/>${dots}`;
    },
    bounds: () => [-110, -65, 110, 65], // カメラ合わせ用 [左, 上, 右, 下]
    radius: 100,                        // リンクが接続する縁。数値なら円、[横, 縦] なら矩形（横長の図形向け）
  },
}
```

守ること:

- 色は CSS 変数（`var(--h-blue-top)`、`var(--ink)` など）で指定する。直接の色コードはダークテーマで破綻する
- 輪郭は `class="outline"`（ink の実線）を使う。文字は `ctx.pill()` に載せる
- 変化を見せたい量は `props` に入れる。`props` が変われば再描画される

## 11. 撮影して確かめる

図はデータで書くが、正しいかどうかは目で見るまでわからない。

```bash
npm run capture -- --lesson <id>                      # 全ステップ
npm run capture -- --lesson <id> --steps 3,7          # 一部だけ
npm run capture -- --viewports desktop,mobile --themes light,dark
```

`captures/` の画像を開き、次を確かめる。

- 物・カード・ラベルが重なっていないか。線が物を横切っていないか
- ラベルがすべて読めるか。上の面からはみ出した文字がないか
- 変化した場所が、ひと目でわかるか
- 粒子が意図した経路を流れているか（静止画なので、位置から判断する）
- 前のステップの画像と並べたとき、変わっていない物が同じ位置にあるか
- モバイルで、カメラが変化した部分を映しているか
