# 学習設計: コース → レッスン → ステップ

このスキルが作るサイトの質は、見た目より先に「学習の単位の切り方」で決まる。
ここに書いた数値は、手本としたサイト（40 レッスン・445 ステップ）の実測から導いた目安。`npm run validate` は、この目安から大きく外れたものを警告する（警告の境目は目安より少し緩い）。

## 目次

1. 中心にある考え方
2. コースの設計

## 1. 中心にある考え方

**1 ステップ = 図の状態変化 1 つ。** 読者は「次へ」を押すたびに、図の中で 1 つのことが起き、その理由を 2 段落で読む。
長い文章に静止画を挟む教材との決定的な違いはここにある。読者の注意は一度に 1 つの因果にしか向けられないので、それに合わせて教材の粒度を切る。

**解決策より先に、問題を見せる。** 読者が「なぜそれが要るのか」を体感する前に仕組みを説明しても、暗記になる。
だから各レッスンは、動いている状態を壊すところから始まり、解決策は次の問題を生む。

**同じ変化を 4 つの経路で示す。** 図の動き、本文、指標の数値、差分リスト。どれか 1 つを見落としても、残りで追える。

**名前は体験の後に付ける。** 用語・定理・パターン名は、その現象を図で見せた後に出す。名前が「さっき見たもの」のラベルになる。

## 2. コースの設計

### 規模

| 単位 | 目安 |
|---|---|
| モジュール | 3〜11 レッスン。1 つの大きな問い（「どう速くするか」「どう壊れにくくするか」）でまとめる |
| レッスン | 8〜14 ステップ、読了 8〜15 分 |
| コース全体 | 小さく始めるなら 1 モジュール 3〜5 レッスン。大きくても 40 レッスン程度 |

### 順序は「次の問い」でつなぐ

各レッスンの最後に、次のレッスンへ進む動機を 1 文で書く（`callout.kind: 'next'`）。この 1 文が書けない並びは、順序が間違っている。

- 良い: 「サーバーを増やした。では、同じユーザーの次のリクエストが別のサーバーに届いたら、何が壊れるか」
- 悪い: 「次はステートレス設計について学びます」

設計の手順:

1. 題材の概念を列挙し、依存関係（A を知らないと B が分からない）を洗い出す
2. 1 つの舞台（小さなシステム、1 つのプログラム、1 人の利用者）を決め、それを育てていく物語として並べる
3. 隣り合うレッスンの間に「前の解決策が生んだ問題」を書く。書けなければ順序か分割を見直す
4. 最初のモジュールで「ものさし」（何を測るか、どの数字を気にするか）を作る

### 難易度は「のこぎり型」

コース全体で単調に難しくしない。モジュールの中で上げ、次のモジュールの頭で入門レベルに戻す。
読者は新しい話題の入口で一息つける。上級のレッスンは全体の 1 割以下でよい。

### 舞台と登場人物を使い回す

同じ題材（同じショップ、同じ座席の予約、同じ 2 人の利用者）を複数のレッスンで使う。
読者は設定を覚え直す必要がなく、「同じ場面を別の角度から見る」ことで概念同士の関係がわかる。

### 総合演習の前に「型」を教える

最後のモジュールで総合的な設計・応用を扱うなら、その前に手順そのもの（要件 → 見積もり → 最小の案 → 壊れる点 → 改善 → 決定の表）を 1 レッスン使って教え、演習レッスンはすべてその型に従わせる。

## 3. レッスンの設計

### レッスン定義に必要なもの

| 項目 | 基準 |
|---|---|
| `summary` | 1 文のフック。問い・逆説・対比で書く。「〜について学びます」は不可 |
| `goals` | 3〜6 個。それぞれが「到達するステップ番号」を持つ。そのステップに着くとチェックが点く |
| `metrics` | 3〜5 個。レッスンを通して値が動くものだけ。閾値で良・注意・悪が決まる |
| `legend` | 図を流れる粒子の種類。コースで定義したものから選ぶ |

### 骨格

1. **最初のステップ**は `setup`（壊れる前の平穏）か `problem`（症状）。定義から始めない
2. **問題 → 解決の往復を 3〜5 回。** 素朴な解 → 破綻 → 改良 → さらに破綻 → 本格的な解
3. **Case ステップを 1〜3 個。** 実務で実際に起きる事故。見出しを「Case: …」で始める
4. **選択肢があるところに `tradeoff`** と比較表
5. **最後は `recap`。** 要点 4〜5 個（太字のキーワードつき）と、次のレッスンへの問い

### 規模の上げ方

同じ図のまま数値だけを上げて限界を体験させる（利用者 1,000 人 → 7,000 人 → 9,600 人）。
新しい物を足すステップと、数値を上げて壊すステップを交互に置くと、起伏ができる。

### 前提知識と相互参照

- 前提の章を別に設けない。必要な前提は「前のレッスンで見たとおり、…」と 1 文で**再掲**する（再説明はしない）
- 他のレッスンへの参照は `[[lesson-id#3|表示する文]]` でリンクにする
- 参照の型: 復習（前のレッスンではこうだった）/ 予告（これは次のレッスンで直す）/ 対比（前は 1 つに届けた、今度は全員に届ける）/ ステップ内（ステップ 1 の数字を覚えているだろうか）

## 4. ステップの役割（chapter）

| chapter | 役割 | 手本での比率 |
|---|---|---|
| `setup` | 壊れる前の状態、または課題の提示 | 5% |
| `problem` | 症状・破綻を見せる。Case もここ | 27% |
| `solution` | 構造を変えて問題を直す | 22% |
| `technique` | 仕組みを 1 つ足す、内部を詳しく見る | 24% |
| `tradeoff` | 選択肢の比較と代償 | 4% |
| `insight` | 一般化する、名前を与える | 9% |
| `recap` | まとめ（各レッスンに 1 つ） | 9% |

役割はタイムラインの点とバッジの色になり、読者はレッスンの起伏（問題と解決の往復）を一目で読める。
`problem` が全体の 4 分の 1 を占めることに注目する。説明ばかりのレッスンは、この比率が崩れている。

規則（検証スクリプトが検査する）:

- `solution` の前には必ず `problem` がある
- `problem` は 1 レッスンに 2 つ以上
- 最後は `recap`

## 5. レッスンの型（題材別）

| 型 | 向いている題材 | 流れ |
|---|---|---|
| 積み上げ型 | 処理の流れ、内訳、見積もり | `technique` を連続させて 1 つずつ足す。指標が主役で、合計が積み上がっていく |
| 比較型 | 技術選定、方式の違い | 選択肢を順に試し、最後に表で「どれを、どこで」 |
| 理論型 | 定理、原理、不変条件 | 平穏 → 壊す → 選択肢 → 名前を明かす → 精緻化。名前は中盤以降 |
| 攻防型 | セキュリティ、信頼性 | 攻撃・障害を Case として連続させ、1 つずつ防ぐ |
| 総合設計型 | 設計演習、応用 | 課題 → 数字を置く → 最小の案 → 壊れる点 → 改善 → 決定の表（問い・決定・理由） |

## 6. 定着の仕組み

手本としたサイトには、能動的に思い出させる仕掛けがなかった。この雛形はそこを補っている。

| 仕掛け | 使いどころ |
|---|---|
| **予測問題**（`predict`） | 結果が直感に反する**そのステップ**に置く。読者が答えるまで図は 1 つ前の状態で止まり、答えを選ぶとそのステップの図が動いて答えを見せる。1 レッスンに 1〜3 個 |
| **つまみ**（`knobs`） | 動かすと図と指標が変わる。トレードオフのあるパラメータ（良くなる値と悪くなる値の両方がある）か、不変条件（どう動かしても変わらない量がある）に使う |
| **学習目標のチェック** | 目標を、内容がわかるステップに結び付ける。最後の目標はレッスン終盤に置く |
| **recap の要点** | チートシートのページに自動で集まる。単独で読んで意味が通る文にする |
| **用語集** | `==用語==` で印を付けた語が載る。定義は 1〜2 文 |
| **完了の条件** | 最後まで到達し、かつ予測問題にすべて答えること。読み飛ばしは完了にならない |

予測問題の作り方:

- 問いは「次に何が起きるか」。知識の再生（〜とは何か）ではなく、いまの図から推論させる
- 誤答の選択肢は、よくある誤解から作る。でたらめな選択肢は学びにならない
- **そのステップの見出し（`title`）と `short` で答えを明かさない。** 見出しは回答前から見えている。「1 億行でも 4 ページ」ではなく「行が 100 倍になったら、何ページ読むか」と書く
- `explain` は、正解した人にも間違えた人にも意味が通るように書く（「正解です」で始めない）

## 7. 設計時の自己点検

- [ ] 隣り合うレッスンの間に「次の問い」が 1 文で書けるか
- [ ] 各レッスンの最初のステップは、定義ではなく状況か
- [ ] 解決策のステップの前に、それを必要とする問題が図で見えているか
- [ ] 用語は、現象を見せた後に出しているか
- [ ] 指標はレッスンを通して動き、悪化する場面があるか
- [ ] Case（実際の事故）が入っているか
- [ ] 予測問題は、直感に反する結果を見せるステップに置いてあるか（そのステップの図が答えになる）
- [ ] recap の要点は、そこだけ読んで役に立つか
