# インタラクティブ学習サイトを作る

題材を渡されたら、**図が主役で、1 ステップに 1 つの変化だけが起きる**学習サイトを作る。
読者は「次へ」を押すたびに図の中で 1 つのことが起きるのを見て、その理由を 2 段落で読み、指標の数値で良し悪しを確かめる。

質を決めるのは次の 4 点で、どれも雛形と規範が支えている。

1. **粒度**: 1 ステップ = 図の状態変化 1 つ。本文は 2 段落
2. **順序**: 問題が先、解決が後。解決策が次の問題を生む
3. **同期**: 図・本文・指標・差分リストが、同じ変化を別の形で示す
4. **記号体系**: 同じ役割は同じ色と形。影・輪郭・書体・動きは少数の規則から外れない

図のエンジンと画面は雛形にあるので、作り直さない。力を注ぐのは**カリキュラム、ステップの文章、図の設計、事実の正確さ**。

## 同梱物

| パス | 内容 | いつ読むか |
|---|---|---|
| `assets/template/` | 動作する雛形（Vite + TypeScript、実行時の依存なし）。サンプルレッスン 1 本つき | 手順 4 で複製する |
| `references/learning-design.md` | コース → レッスン → ステップの設計規範と数値基準 | 手順 2 の前に必ず |
| `references/step-writing.md` | 本文・見出し・callout・差分の書き方、良い例と悪い例 | 手順 5 の前に必ず |
| `references/scene-design.md` | 図の設計。記号体系、配置、粒子、指標、題材別の例 | 手順 3 と 5 の前に必ず |
| `references/content-schema.md` | 雛形の構成、型の早見表、コマンド | 手順 4 で |
| `references/visual-system.md` | テーマ、影・輪郭・色・書体・動きの規則 | テーマを選ぶとき、見た目を変えるとき |
| `references/quality-bar.md` | 完成の基準 | 手順 7 で必ず |

## 手順

### 1. 要件を確かめる

次を確認する。依頼から読み取れるものは聞かずに決め、決めた内容を伝える。

- **題材**と、その中で扱う範囲
- **読者**: 何を既に知っていて、何を知らないか
- **到達点**: 読み終えたとき、何ができるようになっているか
- **規模**: 指定がなければ 1 モジュール 3〜5 レッスンを提案する。まず 1 レッスンを完成させる進め方を勧める
- **言語**（既定は日本語）と**出力先のディレクトリ**

### 2. 調べて、カリキュラムを設計する

`references/learning-design.md` を読む。

題材の事実を一次情報で確かめる（ライブラリ・フレームワーク・規格は context7 や公式ドキュメント）。
教材の誤りは読者に長く残るので、数値・仕様・挙動は記憶に頼らず確認し、版と日付を控える。
手元で動かせる題材（データベース、言語処理系、コマンド、API）は、**実際に動かして数値と出力を取る**。指標の値、予測問題の正解、つまみの式の傾きは、実測に合わせる。文書だけで組み立てた数値は、動かすと食い違うことがある。

そのうえで設計する。

- 1 つの舞台（小さなシステム、1 つのプログラム、1 人の利用者）を決め、それを育てる物語として並べる
- 各レッスンについて、**1 文のフック**、**ステップの役割の列**（問題 › 解決 › しくみ › 問題 › …）、**指標**、**予測問題を置く場所**、**次のレッスンへの問い**を書く
- 隣り合うレッスンの間に「前の解決策が生んだ問題」が書けなければ、順序か分割を見直す

**この設計をユーザーに示し、承認を得てから先へ進む。** レッスンを書いた後の構成変更は高くつく。
ユーザーに確認できない状況（自動実行、任せると言われている）では、自分で決めて進み、決めた内容と理由を引き渡しのときに伝える。

### 3. 題材の記号体系を決める

`references/scene-design.md` の 1〜3 節を読む。レッスンを書く前に、コース全体で使う記号を決める。

- **役割**（何が「物」か）→ 色とアイコン。6〜10 個
- **粒子**（何が「流れ」か）→ 色と形。4〜8 個
- **指標**（何を「測る」か）→ 名前・単位・閾値。読者にとっての結果を測り、根拠のある閾値を置く
- **投影**（`iso` か `flat`）と**テーマ**（`paper` / `slate` / `studio`。選び方は `references/visual-system.md` の 2 節）

### 4. 雛形を複製する

```bash
cp -R <このスキルのディレクトリ>/assets/template/. <出力先>/
cd <出力先> && npm install
npm run check        # まず雛形のままで全部通ることを確かめる
```

撮影と通し確認は手元の Chrome を使う。Chrome がない環境では `npx playwright install chromium` を一度実行する。

`references/content-schema.md` で構成を把握し、サンプルの `src/content/course.ts` と `src/content/lessons/event-loop.ts` を読む。
サンプルは書き方の手本になる。構造（図のヘルパー関数、ステップの並び）を手本にして自分の題材で書く。

`src/content/course.ts` を自分の題材に書き換える: `id`・`title`・`tagline`・`theme`・`projection` と、手順 3 の記号体系（`roles`・`flowKinds`・`metrics`）、`glossary`、`modules`。サンプルの役割・粒子・指標・用語は残さない。足りないアイコンは `src/engine/icons.ts` に足す。
自分のレッスンが 1 本できたら、`src/content/lessons/event-loop.ts` と、その import を消す。単体テストは `tests/fixtures/` の固定データで回るので、サンプルを消しても落ちない。

### 5. レッスンを 1 本、最後まで仕上げる

`references/step-writing.md` と `references/scene-design.md` の残りを読む。

量産する前に 1 本を完成させる。記号体系や配置の問題は、1 本を通して初めて見つかるからである。

1. 図のヘルパー関数を書く（共通の配置を持ち、各ステップは違いだけを渡す）。後のステップで増える物の場所を最初から空けておく
2. ステップを書く。各ステップで、図の差分・本文 2 段落・callout・差分リスト・指標・代替テキストをそろえる
3. 予測問題を、結果が直感に反するステップに置く。つまみを、トレードオフのあるステップに置く
4. `npm run validate` を通す
5. **`npm run capture -- --lesson <id>` で全ステップを撮影し、画像を 1 枚ずつ開いて見る。** 重なり、線の交差、読めない文字、変化のわかりにくさは、ここでしか見つからない。直して撮り直す
6. モバイルとダークも撮る（`--viewports desktop,mobile --themes light,dark`）

撮影は 1 枚あたり約 3 秒かかる（図の動きが落ち着くのを待つため）。13 ステップ × 4 通りで 3 分ほどになるので、書いている途中は `--steps 3,7` のように絞り、全体を撮るときは時間の上限を長めに取るかバックグラウンドで走らせる。

この 1 本をユーザーに見せられる状態にしてから、残りへ進む。

### 6. 残りのレッスンを書く

同じ手順で書き足し、`course.ts` の `modules` に並べる。

レッスンが多いときは、レッスン単位でサブエージェントに分担できる。その場合は、完成した 1 本目・`course.ts`（記号体系）・3 つの規範（learning-design / step-writing / scene-design）・そのレッスンの設計（手順 2 の成果）を渡し、検証と撮影まで行わせる。
記号体系（役割・粒子・指標）を足す必要が出たら、各自で足させず、こちらでまとめて `course.ts` に反映する。

レッスン間の参照は `[[lesson-id#3|表示する文]]` でリンクにする。recap の最後は、次のレッスンへの問いで終える。

### 7. 仕上げて確かめる

`references/quality-bar.md` を上から順に確かめる。

```bash
npm run check
npm run capture -- --viewports desktop,mobile --themes light,dark --pages
```

- `validate` の error は 0 件。warn は 1 件ずつ読み、直すか、残す理由を言えるようにする
- 撮影した全ステップを見る
- **内容の正しさは、フレッシュコンテキストのレビュアー（別のエージェント）に確かめさせる。** 題材の専門家として、事実の誤り・誤解を招く単純化・予測問題の正解を検証させる。書いた本人には見えない誤りがある
- 最初のレッスンを、初めての読者のつもりで最後まで進める

### 8. 引き渡す

- 起動方法（`npm install` → `npm run dev`）と公開方法（`npm run build` → `dist/` を静的ホスティングに置く）
- レッスンの足し方（`src/content/lessons/` にファイルを足し、`course.ts` に並べる）
- 確認できなかったこと、単純化したこと、次に足すとよいレッスン

## 既存のサイトにレッスンを足す・直す

雛形から作られたサイト（`src/content/course.ts` と `src/engine/stage.ts` がある）が既にあるなら、手順 4 を飛ばす。
`course.ts` の記号体系と既存のレッスンを読み、同じ舞台・同じ色・同じ語り口で書き足す。手順 5〜7 は同じ。

## 守ること

- **エンジンと画面を作り直さない。** 雛形で表せない図形は `Course.renderers`（`scene-design.md` の 10 節）で足す。それでも足りないときだけ、理由を持ってエンジンに手を入れ、`npm test` を通す
- **撮影を省かない。** 図はデータで書くが、正しいかどうかは見るまでわからない
- **見た目の規則を崩さない。** 影は 2 系統、輪郭は ink、書体は 2 つ、動きは語彙から。新しい色や影を足したくなったら、`visual-system.md` の 11 節を読む
- **他の教材の文章・図・構成を写さない。** 題材の事実は一次情報から取り、説明・例・図は自分で組み立てる
- **分量の基準を超えたら、削る前に分ける。** 1 ステップに 2 つのことを書いているのが原因であることが多い
