# PR レビューガイド投稿

変更ファイルごとに「重要度 + レビューポイント」を書いたファイル単位コメント（GitHub の file-level review comment）を作成し、1 つのレビューとしてまとめて PR に投稿する。コメントは Files changed 画面で各ファイルのヘッダー直下に表示される。

## 方針（なぜこの形式か）

- **ソースコードには書き込まない。** レビュー向けの説明コメントはマージ後にノイズとして残るため、PR のレビューコメントとして投稿する。ユーザーが「ファイル自体に」と言った場合も、この理由を添えて PR コメント方式を提案する（それでもコード内を希望されたら従う）。
- **個別コメントではなく 1 レビューにまとめる。** ファイル数分の個別コメントは PR タイムラインと通知を汚す。ペンディングレビューにスレッドを積んでから submit すれば、通知は 1 回で済む。
- **全ファイルを網羅する。** テスト・設定・ドキュメントも省略しない。「低」の明示は「読み飛ばしてよい」という情報であり、それ自体がレビュアーの時間を節約する。

## 手順

### 1. PR と変更内容の把握

```bash
gh pr view --json number,title,url,files,headRefOid
```

PR 番号が指定されていなければ現在のブランチの PR を使う。diff を取得してスクラッチパッドに保存し、**必ず中身を読んでから**コメントを書く（ファイル名だけで書いたポイントは的外れになる）:

```bash
gh pr diff <PR番号> > <scratchpad>/pr.diff
grep -n '^diff --git' <scratchpad>/pr.diff   # 各ファイルの開始行を把握し、セクション単位で Read する
```

大きなテストファイルは全行読む必要はないが、何を検証しているか（観点の一覧）は把握する。

### 2. 重要度の分類

正直に分布させる。全部「高」ではレビュアーの優先順位付けに役立たない。

| 重要度 | 目安 |
|---|---|
| 🔴 高 | 中核ロジック、public API の破壊的変更、セキュリティ関与、正規表現・並行処理など繊細なコード、契約（型・インターフェース）変更の起点 |
| 🟡 中 | 契約変更への対応、エラー処理、状態遷移の拡張、主要な新規テスト |
| 🟢 低 | リネーム等の機械的追随、モック、スタイル、設定、ドキュメント |

### 3. コメントの作成

`comments.json` をスクラッチパッドに作る。`path` は diff に現れるリポジトリルート相対パスと完全一致させること。

```json
[
  {
    "path": "src/api/client.ts",
    "body": "🔴 **重要度: 高** — 本 PR の中核。〈ファイルの役割を一言で〉\n\n**ポイント:**\n- 〈レビュアーが確認すべき点。仕様との対応、壊れやすい箇所、設計判断の理由〉\n- 〈…〉"
  },
  {
    "path": ".gitignore",
    "body": "🟢 **重要度: 低** — 〈一言で済むものは 1 行でよい〉"
  }
]
```

書き方の要点:
- ポイントは「何をしたか」の要約ではなく「**どこを確認してほしいか**」を書く。仕様書番号・設計判断の理由・壊れやすい箇所（タイミング競合、境界条件、フォールバック）が特に価値が高い。
- 契約変更の起点になるファイルには「最初にこのファイルを読むのがおすすめ」と明記する。
- 低重要度のファイルは 1〜2 行で十分。

### 4. サマリーの作成

`summary.md` をスクラッチパッドに作る。内容は次の 2 点:

1. **凡例**: 🔴 高 / 🟡 中 / 🟢 低 の意味
2. **おすすめの読み順**: 契約・型定義 → 中核実装 → 呼び出し側 → UI → テスト・設定 の順が基本

### 5. 投稿

```bash
<このスキルのディレクトリ>/scripts/post_review.sh --pr <番号> \
  --comments <scratchpad>/comments.json \
  --summary <scratchpad>/summary.md
```

投稿前に `--dry-run` を付けて内容を確認できる。スクリプトは「ペンディングレビュー作成 → GraphQL で FILE スレッド追加 → event=COMMENT で submit」を一括で行い、成功時にレビュー URL を出力する。ユーザーには URL とともに、重要度の内訳（高/中/低の件数と代表ファイル）を報告する。

## 注意点

- **既存のペンディングレビューがあると失敗する。** GitHub は 1 PR につき 1 人 1 件しかペンディングレビューを持てない。スクリプトは検出して中断するので、勝手に削除せず、ユーザーに確認する（ユーザーが下書き中のレビューかもしれない）。
- **自分の PR には event=COMMENT でしか submit できない**（APPROVE / REQUEST_CHANGES は不可）。スクリプトは COMMENT 固定なので通常は意識不要。
- スレッド追加が途中で失敗した場合、ペンディングレビューは残る。原因（大抵は path の不一致）を直し、残ったペンディングレビューを削除してから再実行する。
- コメント本文は日本語で書く（このリポジトリの慣習に合わせる）。
